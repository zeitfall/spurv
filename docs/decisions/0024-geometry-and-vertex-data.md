# 0024. Geometry and vertex data

- Status: Accepted
- Date: 2026-11-10

## Context

[0026](0026-scene-components-and-meshes.md) defines `Geometry` as shared data of the module `geometry` to which a `Mesh` refers, and it leaves the structure of that data open. The plan of the module asks whether the vertex attributes are interleaved or stored separately, and milestone 3 ([architecture.md](../architecture.md#milestones)) renders cubes with positions, normals, and texture coordinates.

Several constraints shape the structure. The module `geometry` cannot import `gpu` or name a type of WebGPU ([0010](0010-module-boundaries-and-layers.md)), so it describes its data without them, although an enum object may carry the strings that WebGPU expects ([api-conventions.md](../api-conventions.md#enumerations)). The prepare phase uploads the data of a geometry into the render world, which is separate from the main world ([0004](0004-frame-phases.md)), so the layout of a GPU buffer need not repeat the layout of the data on the CPU. Internal collections are never returned, and this protection has to hold for a consumer of plain JavaScript ([0018](0018-encapsulation-and-inheritance.md)). A change of the data has to become visible to the renderer, and the library already reports changes through version counters ([0015](0015-transform-versions.md), [0022](0022-render-device-resources.md)). Code that changes a single vertex addresses it by its index, and it should not compute an offset into an array. The attributes of milestone 3 consist of 32-bit floats only, whereas glTF in milestone 6 brings integer and normalized formats, and one attribute, such as a color, then occurs in several formats.

Bevy, the architectural reference of the project, stores the values of each attribute of its `Mesh` separately under a `MeshVertexAttribute`, which consists of a name, a unique id, and a format. Its indices are optional and consist of either 16-bit or 32-bit integers, and it packs the attributes into a single vertex buffer when it prepares a mesh for the GPU. A predefined attribute fixes its format, so an insertion of values in another format fails, and attributes of different lengths are truncated to the shortest one.

## Decision

A geometry stores each vertex attribute separately, as Bevy does, and it does not interleave them. The renderer copies the data into its own buffers in any case, so it can choose the layout of those buffers when it uploads them, and the storage on the CPU does not restrict that choice. A consumer therefore computes no strides and no offsets, and an attribute can be added or replaced without a change to the others. An interleaved array was rejected, because it saves only one copy for each upload and makes the consumer responsible for the layout.

The enum object `VertexFormat` names the format of an attribute. Its values are the strings of the WebGPU enumeration of vertex formats, as the API conventions require, so the renderer passes a value to WebGPU without mapping. It contains `FLOAT32X2` and `FLOAT32X3`, which are the formats of the attributes of milestone 3, and a format is added when the library first uses it. Two tables of the module, keyed by the format, hold the number of components of each format and the class of the typed array that stores it. Both formats of milestone 3 are stored in a `Float32Array`, and the second table exists nevertheless, so that an attribute selects its storage by its format from the start.

The class `VertexAttribute` holds the data of one attribute. Its constructor accepts an `ArrayLike<number>` and a `VertexFormat`. The format is a parameter, and the number of components is not, because the number of components states neither the type of the stored values nor their normalization, so a signature built on it could not admit the formats of milestone 6 without a breaking change. A format that is inferred from the class of the given typed array was rejected for the same reason, since it requires an additional flag for normalization and leaves a plain array of numbers without a format. The constructor throws a `RangeError` for a value that is not a `VertexFormat` and for an array whose length is zero or is not a multiple of the number of components.

The constructor copies the given array, and the class never returns its copy. A consumer therefore cannot change the data without the knowledge of the attribute, and the rule of 0018 holds without an exception. The copy is created with the static method `from` of the class that the table holds for the format, because the constructor of a typed array shares the memory of an `ArrayBuffer` that it receives, whereas `from` copies every input and produces an empty array for an `ArrayBuffer`, which the validation of the length rejects. An attribute that adopts the given array was rejected, because the consumer retains a reference through which the data changes while the version does not. The data is stored in the format of the attribute, and not in the 64-bit floats in which `math` computes ([0005](0005-math-conventions.md)), because the data is uploaded unchanged and the extract phase then has nothing to convert.

`VertexAttribute` exposes the getters `format`, `vertexCount`, and `version`. The getter of the format carries no prefix, because an attribute has a single format, whereas the count names its unit, because an attribute also has a number of components and a number of stored elements. The methods `setFromArray(array, arrayOffset = 0)` and `writeToArray(array, arrayOffset = 0)` transfer the data of every vertex, and the methods `setVertexFromArray(vertexIndex, array, arrayOffset = 0)` and `writeVertexToArray(vertexIndex, array, arrayOffset = 0)` transfer the components of one vertex. The last parameter is named `arrayOffset`, as [api-conventions.md](../api-conventions.md#standard-methods) defines, because an attribute is itself a sequence of vertices, so a bare offset could denote a position in either sequence. Their names follow the standard methods and the rules of `write` in [api-conventions.md](../api-conventions.md#copy-and-write), the assigning methods return the attribute, and the writing methods return their target. Each of them transfers exactly as many elements as the format prescribes, so one pair of methods serves every format. Methods that accept the components as separate numbers were not introduced. They require one method for every number of components, and a call with too many components would overwrite the next vertex, since a hot path does not validate its arguments ([code-style.md](../code-style.md#errors)). Such methods, or methods that accept a vector, can be added later without a breaking change.

Every assigning method increases `version` by one, and the renderer compares versions during the prepare phase, in the manner of 0015 and 0022, to decide which attribute it uploads again. A flag that the consumer sets after a change was rejected, because an omitted flag leaves stale data on the GPU without any error.

The renderer reads the array of an attribute through the function `getVertexAttributeArray`, which the module exports from its `index.ts` with the tag `@internal` and which `src/index.ts` does not export again, as [0010](0010-module-boundaries-and-layers.md) provides. The function reads a side table ([code-style.md](../code-style.md#module-scope)) in which the constructor records the array. The renderer thereby passes the array to WebGPU without a further copy.

The enum object `VertexAttributeName` names the role of an attribute in a geometry and contains `POSITION`, `NORMAL`, and `UV`. A string that the consumer writes was rejected for the reason that 0026 gives for the lookup of components by class: a misspelled name would produce an attribute that every shader ignores, without any error. The name and the format are separate, unlike in Bevy, where the attribute fixes its format, so that an attribute which occurs in several formats requires no additional names.

The class `Geometry` is created without arguments and is assembled through its methods, which return the geometry. The method `setAttribute(name, attribute)` stores the attribute under the given name and replaces an attribute that the geometry already holds under that name. It throws a `RangeError` for a value that is not a `VertexAttributeName`, and for an attribute whose vertex count differs from that of an attribute held under another name. Bevy truncates such attributes to the shortest one, whereas an error here indicates the call that introduces the inconsistency. The method `getAttribute(name)` returns the attribute or null, and the getter `vertexCount` returns the vertex count of the attributes, or zero for a geometry without attributes. An attribute does not belong to a geometry, so several geometries may hold the same attribute.

The indices are optional and are not an attribute. The method `setIndices(indices)` accepts a `Uint16Array`, a `Uint32Array`, or null, and it copies a given array into an array of the same class, from which the renderer derives the format of the index buffer. It throws a `TypeError` for any other value and a `RangeError` for an array whose length is zero or is not a multiple of 3. The getter `indexCount` returns the number of indices, or zero for a geometry without indices, and the method `writeIndicesToArray(array, arrayOffset = 0)` writes them into the given array. The renderer reads the copy through the function `getGeometryIndexArray`, which is exported in the same manner as `getVertexAttributeArray`. A class of indices with access to a single index was rejected, because indices are replaced as a whole. A `VertexAttribute` that holds indices was rejected, because the formats of indices form a separate enumeration in WebGPU and a vertex format would misstate them.

`Geometry` exposes the getter `version`, which `setAttribute` and `setIndices` increase by one. It reports a change of the composition of the geometry, whereas the version of an attribute reports a change of its data, so the renderer compares both.

The topology of every geometry is a list of triangles, which is the only topology that milestone 3 requires. A geometry assigns no shader locations. It states which attributes it holds, and the decision on the attributes that a shader requires belongs to the design of `renderer` and `materials`.

The module defines no component. A node refers to a geometry through its `Mesh`, as 0026 defines.

The module provides no predefined shapes. Shapes that are generated from parameters, such as a cube of given dimensions or a sphere with a given number of segments, are left to a later ADR, which also decides their form under the restriction of inheritance in 0018. A single function that returns a cube of fixed size was rejected, because it would establish a form for shapes before that decision. Until then, an example supplies the arrays of its shapes, as `02-hierarchy` does.

## Consequences

- The open question of the `geometry` plan on the storage of the attributes is resolved.
- The renderer chooses between one GPU buffer for each attribute and a single packed buffer without a change to the public API.
- A change of the data cannot bypass the version of its attribute.
- Every attribute and every array of indices is copied once at its creation, so a consumer cannot share memory with a geometry, and the memory of a large model is held twice until the consumer releases its own array.
- A change of one vertex causes the renderer to upload the whole attribute. Ranges of changed vertices can be introduced later without a breaking change.
- The methods that transfer data validate nothing. A vertex index outside the attribute changes no data but increases the version, and a source array that is too short leaves the remaining components unchanged, in the manner of the defaults of `setFromArray` in `math`.
- The function `getVertexAttributeArray` is the first export of the library with the tag `@internal`. The package exposes only its root entry, so the function is unreachable through the name of the package, although a direct path to a file of the package reaches it. The protection therefore prevents inadvertent use and not deliberate circumvention.
- A new format requires an entry in `VertexFormat` and in both tables. A format that is not stored in a `Float32Array` also widens the type of the array that `getVertexAttributeArray` returns, and it requires a decision on whether the methods of a normalized format accept stored or normalized values.
- The name of an attribute does not determine its format, so the renderer decides whether the format of an attribute suits a shader.
- The set of names is closed. Attributes for WGSL that the consumer supplies require a new ADR that opens it.
- An attribute cannot be removed, and the vertex count of a geometry that holds attributes under two names cannot change, so a consumer creates a new geometry in both cases.
- An attribute that several geometries hold changes in all of them at once.
- The indices are not compared with the vertex count, and the vertex count of a geometry without indices is not required to be a multiple of 3.
- The example of milestone 3 repeats the vertex data of the cube of `02-hierarchy`, since the library provides no shapes.
- `Geometry` departs from Bevy in the separation of the name from the format and in the error for attributes of different vertex counts.
