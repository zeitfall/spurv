# 0022. Render device resources

- Status: Accepted
- Date: 2026-11-09

## Context

[0020](0020-gpu-layer-scope.md) gives the module `gpu` a class of buffers and a class of textures, each of which holds its current WebGPU object and replaces that object on a resize, and it leaves open how a replacement is reported. [0021](0021-render-device.md) requires that these classes are created by `RenderDevice` and receive the `GPUDevice` from it.

Several properties of WebGPU shape these classes. The size of a `GPUBuffer` or a `GPUTexture` is immutable, although both objects expose the properties from which a replacement is created, such as `size`, `usage`, and `format`. A bind group refers to one concrete `GPUBuffer` and becomes invalid when that buffer is destroyed. A render pass receives a `GPUTextureView`, which is a new object on every call to `createView` and becomes invalid together with its texture. A buffer receives data either through `queue.writeBuffer`, which requires the usage `COPY_DST`, or once at its creation through `mappedAtCreation`, which requires that the buffer is unmapped before its use. Both paths require a byte count that is a multiple of 4, so three 16-bit indices, which occupy 6 bytes, are rejected unless the buffer is padded. A new buffer contains zeros.

## Decision

The classes are named `RenderDeviceBuffer` and `RenderDeviceTexture`, since each resource belongs to the `RenderDevice` that creates it, and the shared prefix places their files next to the file of that class. The `GPU` prefix is reserved for WebGPU. `DeviceBuffer` and `DeviceTexture` were rejected because a device also denotes hardware unrelated to rendering, such as a gamepad. A bare `Buffer` resolves to the global type of Node when an import is missing under the development configuration of TypeScript, and a bare `Texture` remains available to the texture asset of milestone 6. `RenderBuffer` and `RenderTexture` were rejected because these terms already denote an image attachment and a render target.

Buffers of every purpose share the single class `RenderDeviceBuffer`, because uploading, resizing, and destruction are identical for all of them and only the usage flags differ. Subclasses for each purpose provide no checks at compile time, since the renderer calls the plain `GPURenderPassEncoder`, which accepts any `GPUBuffer`. The format of the indices belongs to the data of a geometry, which the renderer holds when it binds an index buffer.

The constructor of each class accepts a `GPUDevice` and a WebGPU object that is already created, as the constructor of `RenderDevice` does, so that an instance is never partially initialized and the class reads the size and the usage from that object. The static method `RenderDeviceBuffer.create` accepts a `GPUDevice`, a size, and usage flags. The static method `RenderDeviceBuffer.createWithData` accepts a `GPUDevice`, an `ArrayBufferView`, and usage flags. It rounds the size up to a multiple of 4, creates the buffer with `mappedAtCreation`, copies the data, and unmaps the buffer, so that a caller never observes a mapped buffer. Bevy, the architectural reference of the project, offers the same separation through `create_buffer_with_data`. Every buffer retains `COPY_DST`, including one that receives its data at creation, because a resize produces an empty buffer that otherwise could not be filled, and a mode of immutable buffers would make `write` and `resize` conditional.

`RenderDevice` provides `createVertexBuffer`, `createIndexBuffer`, and `createUniformBuffer`, which accept a size, together with `createVertexBufferWithData`, `createIndexBufferWithData`, and `createUniformBufferWithData`, which accept data, and `createDepthTexture`, which accepts a width and a height. These methods return instances of the classes above and add the usage flags of their purpose. Every kind of buffer that [0020](0020-gpu-layer-scope.md) admits therefore offers the same two ways of creation. The methods accept no additional usage flags, because the renderer of milestone 3 requires none.

`RenderDeviceBuffer` provides the method `write(data, bufferOffset, dataOffset = 0)`, which forwards to `queue.writeBuffer` with the same order of offsets. Separate names state which of the two positions each offset denotes, and the offset in the data selects the start of an upload without a new view of the data. It also provides the getters `raw` and `version`, and the methods `resize(size)` and `destroy`. The getter `raw` returns the current `GPUBuffer`, and its name avoids a repetition at a call site such as `vertexBuffer.raw`. It exists, unlike a getter of the `GPUDevice`, because bind groups and render passes remain plain WebGPU objects and accept only a `GPUBuffer`.

Each class reports a replacement through the getter `version`, which increases by one on every replacement. A consumer that retains a WebGPU object, or a bind group created from one, stores the version together with it and compares the two during the Prepare phase of [0004](0004-frame-phases.md), in the same manner as the transform versions of [0015](0015-transform-versions.md). A consumer therefore rebuilds its state at most once per frame, regardless of the number of resizes, and there are no subscriptions to remove. A boolean result of `resize` was rejected because it informs only the caller of `resize` and not a second holder of the resource. An event was rejected because it requires unsubscription and rebuilds once per replacement. Bevy gives every wrapped buffer a unique `BufferId`, which is the source of this polling approach.

A resize to the current size does nothing and leaves `version` unchanged, whereas a resize to any other size, including a smaller one, performs a replacement. A buffer that only grows was rejected, because a depth texture has to match the size of its color attachment exactly and the two classes would then behave differently. A strategy of growth belongs to the renderer, which calls `resize` with the capacity that it selects.

A resize of a `RenderDeviceBuffer` does not preserve the contents of the buffer. [0020](0020-gpu-layer-scope.md) makes preservation conditional on a caller that requires it, and milestone 3 has no such caller, because vertex and index buffers are not resized and the renderer holds the data of uniform buffers in the render world. A consumer that observes a new version writes the data again. Preservation and the usage `COPY_SRC` that it requires are introduced together with the first caller that requires them.

`RenderDeviceTexture` provides the static method `create`, which accepts a `GPUDevice` and a `GPUTextureDescriptor`, the getters `raw`, `view`, and `version`, and the methods `resize(width, height)` and `destroy`. The getter `raw` returns the current `GPUTexture`, so both classes expose their WebGPU objects in the same manner. The class holds the default view of its texture and replaces that view together with the texture, so the renderer reads the current view when it begins a render pass and allocates nothing per frame. `GpuImage` in Bevy likewise stores a texture together with its default view. A replacement retains the dimension, the number of layers, the format, the usage, the sample count, and the number of mip levels of the previous texture. The creation of views from a descriptor is introduced when the renderer first requires it.

## Consequences

- The open question of the `gpu` plan on the report of a replacement is resolved.
- The depth texture requires no version check, since the renderer reads its view when each render pass begins.
- A consumer that retains a bind group and omits the comparison of versions uses a destroyed buffer, and WebGPU reports the failure as a validation error.
- A buffer created with data can be larger than that data, because its size is rounded up to a multiple of 4.
- `write` passes data of a length that is not a multiple of 4 to WebGPU, which rejects it.
- Every consumer of a resized buffer writes its data again.
- A replacement of a texture omits `viewFormats`, because `GPUTexture` does not expose that property. No texture of milestone 3 uses it.
